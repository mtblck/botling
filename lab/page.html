How families could join the package

Recommendation: one package, one shared renderer, and each family as its own entry point. Robots stay exactly as 1.x froze them.

import { botling } from 'botling';          // robots, unchanged
import { animal } from 'botling/animals';   // new, opt-in
import { person } from 'botling/people';
import { monster } from 'botling/monsters';
import { dino } from 'botling/dinos';

animal('matt@botling.me', { size: 48, frame: 'circle', animate: true });
  1. Subpath exports, not a kind option. A kind switch on botling() would pull every family's art into every bundle, and it would blur the fact that each family has its own frozen picture. Separate entry points tree-shake, and robot-only users pay nothing.
  2. Not sibling npm packages, at least at first. Each would need its own releases, tags and copy of the renderer. One package keeps one release and one playground. A family could still graduate to its own package later if it gets its own brand.
  3. Pull the shared core out of the robot code. Cells, paths, frames, palette checks and the animation shell move to an internal module that every family uses. The golden corpus proves robots don't move by a pixel, so this is a 1.x minor under ADR 0006.
  4. Each family freezes on its own. It ships marked experimental until you pick its art, then gets its own ADR, golden corpus and contrast tests, and its own "picture is the API" promise from then on.
  5. Every family needs a 9×9 small version for 24px, the way the robots got one. The 32px wall here shows the 15×15 art shrunk, which is where it starts to blur.
  6. Seeds are salted per family (animal: + seed), so one user's robot and animal don't share hidden patterns. The playground would get a family switcher, with the family in the hash next to the seed.
